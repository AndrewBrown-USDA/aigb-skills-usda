# 13.2.2 -- resolver-core
## Goal
Implement a dependency-free, catalog-backed resolver that deterministically expands ordered skill and loadout roots into a post-order packaged install plan with stable diagnostics.

## Notes
Facts: `catalog/skills.lock.json` is schema version 1 with a `skills` array; entries use `name`, packaged `source_repo`/`source_path`/`source_url`, optional provenance, and version objects whose missing form is `{status:"missing",value:null}`. `normalizeMetadata` preserves legacy provenance aliases and normalizes comma-separated dependency fields. ADR 0006 specifies deterministic depth-first post-order traversal: direct roots preserve request order, loadout members are name-sorted, dependencies preserve declaration order, required edges always select, optional edges require explicit inclusion or force, force outranks exclude, exclude outranks include, and errors produce no partial result. Resolution must remain offline and must use packaged `source_path`, never provenance URLs. The referenced `docs/design/skill-loadouts/skill-loadout-resolution.md` is not present in the checked-out tree; ADR 0006 and the task specification provide the available design facts. Only `scripts/skill-loadouts.js`, `scripts/skill-loadouts-test.js`, and optionally `.scratch/loadout-tests/` are in scope; do not modify generated catalog, installer, CLI, metadata, README, or docs.
## Questions
1. Should a catalog entry's `loadout` field identify a single loadout membership, with all entries sharing that value expanded by `loadout:<name>`?
2. Should `include`/`exclude`/`force` accept only skill names, or also `loadout:<name>` selectors?
3. For a version-shaped catalog value or selector constraint, should every non-plain metadata version object be treated as unsupported, while plain resolved/missing catalog version objects remain accepted?
